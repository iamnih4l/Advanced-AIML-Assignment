# Algorithmic Modeling & Performance Rigor

This document details the machine learning models trained, their evaluation metrics, and the rationale behind the selected final model for the Semiconductor Manufacturing Defect Prediction system.

## Data Splitting Strategy
To avoid data leakage, we utilized a `GroupShuffleSplit` grouping by the `batch_id`. In a manufacturing context, wafers processed in the same batch share exact environmental, temporal, and operator conditions. A simple random split could place wafers from the same batch in both the training and test sets, artificially inflating metrics. `GroupShuffleSplit` ensures entire batches are cleanly partitioned.

## Models Evaluated

### 1. Baseline Model: Logistic Regression
- **Purpose**: Provides a linear, highly interpretable benchmark.
- **Pipeline**: Imputation -> Custom Feature Engineering -> Scaling/Encoding -> SMOTE -> Logistic Regression.
- **Performance**: While Logistic Regression performs adequately on linearly separable data, the non-linear anomalies and complex interactions injected into this dataset limit its predictive power, often resulting in lower Precision-Recall AUC.

### 2. Advanced Model: XGBoost
- **Purpose**: An industry-standard ensemble method (Gradient Boosted Trees) capable of modeling complex, non-linear relationships and interactions without requiring exhaustive manual feature crossing.
- **Pipeline**: Imputation -> Custom Feature Engineering -> Scaling/Encoding -> SMOTE -> XGBClassifier.
- **Hyperparameter Tuning**: We utilized `RandomizedSearchCV` optimizing for `average_precision` (PR-AUC) given the rare-defect nature of the problem. Tuned parameters included `learning_rate`, `max_depth`, `n_estimators`, and `subsample`.

## Metric Selection
Because defective cases represent only ~8.3% of the dataset, naive Accuracy is dangerously misleading. We rely on:
- **Precision**: Of the wafers flagged as defective, how many actually were? (Operationally: Minimizing wasted manual inspections).
- **Recall**: Of the truly defective wafers, how many did we catch? (Operationally: Minimizing defective wafers shipped to customers).
- **PR-AUC (Precision-Recall Area Under Curve)**: The primary metric. It summarizes the trade-off between Precision and Recall specifically focusing on the minority class, making it superior to ROC-AUC for highly imbalanced problems.

## Model Comparison

| Model | Precision | Recall | F1-Score | ROC-AUC | PR-AUC |
|---|---|---|---|---|---|
| Logistic Regression (Baseline) | 0.1818 | 0.5852 | 0.2774 | 0.7426 | 0.3994 |
| XGBoost (Tuned) | 0.7042 | 0.2545 | 0.3738 | 0.7261 | 0.3957 |

*Note: Exact numerical results generated by the pipeline execution can be found in `reports/experiment_log.json`.*

## Conclusion & Serialization
Interestingly, **Logistic Regression** slightly outperformed XGBoost on the primary metric (PR-AUC) and achieved significantly higher Recall (0.5852 vs 0.2545). 

This outcome is highly instructional: because our custom feature engineering in M2 (e.g., `temperature_deviation`, `equipment_stress`, `maintenance_risk`) explicitly linearized the complex relationships in the synthetic data, the Logistic Regression model was able to easily capture the risk profile without needing the deep non-linear splitting of an ensemble tree model. XGBoost over-optimized for Precision (0.7042) at the massive expense of Recall, making it less suitable for a manufacturing context where missing a defect (False Negative) is very costly.

Therefore, the **Logistic Regression** pipeline (which crucially embeds the entire imputation, feature engineering, scaling, encoding, and SMOTE logic) has been selected as the final model. It was serialized via `joblib` to `models/final_defect_prediction_pipeline.joblib`. The backend API will load this exact artifact for inference, ensuring a perfectly reproducible pipeline.
